# v2.0 release defects — go/no-go assessment

> Both defects below are **fixed**. For defects that are still open, see
> [`OPEN_FINDINGS.md`](OPEN_FINDINGS.md).

Two application defects found during the regression run of 2026-11-17
(`tests/runs/2026-11-17-2311-regression/report.md`). Both predate this release
cycle. This document states what was verified, what was not, the root cause of
each, and a recommendation for the coordinated kast 3.0 / kast-web 2.0 tag.

Neither is a remote or unauthenticated compromise. Both are cases where the
application's behaviour does not match what its own UI tells the user.

---

## Defect 1 — the `viewer` role has no authorization behind it

**Status:** verified empirically. **FIXED** 2026-11-18.
**Recommendation:** was fix before tagging 2.0 — done.

### What happens

A user with `role = 'viewer'` — documented in the user-creation form as
"Viewer - Read-only access" — can create and execute scans.

During the regression run, `t_viewer` submitted a fully valid scan form and
the server created scan id 15, which ran to completion against the WebGoat
test target. The scan form is rendered for viewers; nothing in the UI or the
request path prevents the submission.

### Root cause

`/scan/new` (`app/routes/main.py:145`) carries only `@login_required`.

`create_scan()` is otherwise careful about privilege. It gates every
*elevated* capability within scan creation:

| Capability | Gate |
|---|---|
| Active scan mode | `can_run_active_scans` (admin, power_user) |
| Config profiles | `is_power_user or is_admin` |
| `config_overrides` | `is_power_user or is_admin` |
| ZAP automation plans | `is_power_user or is_admin`, plus per-plan `allow_power_users` |
| Remote scan runners | `is_power_user or is_admin` |

What it never checks is whether the user may create a scan **at all**. The
permission model has a floor missing, not a wall. This reads as an oversight
in an otherwise thorough implementation rather than systemic neglect.

Confirming the gap: the string `'viewer'` appears exactly **once** in `app/` —
`app/forms.py:432`, the dropdown label. There is no `can_run_scans` property,
no `viewer` branch, and no decorator anywhere that treats the role as distinct
from `user`.

### Scope

- **Passive mode only.** Active scans are correctly refused for viewers
  (`can_run_active_scans` excludes the role), and the UI additionally renders
  the Active option as `disabled`. Verified both in the UI and by submitting a
  crafted POST with `scan_mode=active`, which was rejected server-side with the
  expected flash.
- **`config_overrides` is not exploitable this way.** A crafted POST injecting
  the field as a non-privileged user was dropped server-side; the column was
  null on the resulting scan.
- **`/logos/upload` (`app/routes/logos.py:91-147`) also has no role check.** A
  viewer could upload a report logo — a shared, prospect-facing whitelabeling
  asset. Established by source inspection: the `logos` blueprint has no
  `before_request` and no blueprint-level guard, the handler body contains no
  role check, and the Add Logo dialog in `app/templates/logos/manage.html` is
  not wrapped in a role conditional. **Since confirmed by execution:**
  `t_viewer` uploaded a logo successfully before the fix. Logo *deletion* was
  already correctly gated (admin or the original uploader).
- Other write routes that lack a role decorator were checked and do enforce
  authorization in the handler body (for example `/auth/users/<id>/delete`
  checks `current_user.is_admin`; `/scans/<id>/transfer` checks owner-or-admin).
  An earlier decorator-only audit overstated this list and should not be relied
  on.

### Why it matters for 2.0

Viewers are internal users created by an administrator, so this is a privilege
boundary within an authenticated application, not an open door. But kast-web
executes scans against targets, and `CLAUDE.md` makes reputational safety a
first-class concern. An account an administrator deliberately designated
read-only being able to initiate scans is a gap between the promise and the
behaviour, and it is cheap to close.

### Proposed fix

1. Add a `can_run_scans` property to `User` (`app/models.py`, beside
   `can_run_active_scans`): `return self.role in ('admin', 'power_user', 'user')`.
2. Gate `create_scan()` on it, with a flash consistent with the existing
   active-scan denial.
3. Hide or disable the scan form for viewers in the index template, matching
   how the Active option is already disabled — defence in depth, not the
   boundary itself.
4. Decide separately whether `/logos/upload` should require the same floor.
5. Add a regression case asserting the denial **with a positive control** (see
   the note on vacuous passes below).

## Defect 2 — public share links are generated but can never be used

**Status:** verified empirically and by exhaustive source search. **FIXED (disabled)** 2026-11-18.
**Recommendation:** was remove the UI for 2.0 and implement in 2.1 — the removal is done.

### What happens

The scan detail page has a "Public Link" tab stating:

> Public links allow anyone with the link to view this scan without logging in.
> Links are view-only and will expire after the specified period.

Generating one appears to succeed: the server mints a token, writes a
`ScanShare` row, records an `AuditLog` entry (`create_public_link`), and
flashes "Public link generated successfully".

No URL is ever produced, and no URL would work if it were.

### Root cause

The feature is incomplete at both ends.

**Nothing surfaces a link.** `app/templates/scan_detail.html:1089` defines a
`#public-link-display` panel with a `#public-link-url` input, both
`display: none`. Nothing un-hides the panel or populates the input. The
"Current Shares" tab labels a share as public but does not render a URL from
the token either.

**Nothing consumes the token.** `share_token` appears in exactly five places
app-wide:

| Location | Use |
|---|---|
| `app/models.py:363` | column definition |
| `app/models.py:402` | `to_dict()` serialization |
| `app/routes/scans.py:1169` | the write, in `generate_public_link()` |
| `app/admin_db.py:172,182` | Flask-Admin explorer config |

It is never read to authorize access. The only routes with a non-integer
`<token>` converter are logo import and password reset. `/scans/<int:scan_id>`
cannot match a token string. An unauthenticated request carrying a valid token
returns 404, which was confirmed during the run.

### Scope

Sharing *with an internal user* works correctly and is unaffected: the
`ScanShare` row is created, the recipient gains access to the scan detail, a
read-only recipient cannot delete it, and revocation removes access. All
verified. Only the **public link** path is dead.

One related observation, not a defect: a scan shared with an internal user does
not appear in that user's `/scans/` list or dashboard, though the detail page
is reachable. The case catalog expects it visible there. Worth a decision, but
it is a UX question rather than a correctness one.

### History

Introduced in `1a2da0b` ("Users: phase 4 - sharing scans", 2025-11-20) and
never functional since. It is not advertised in `README.md` or `CHANGELOG.md`,
so no published claim depends on it.

### Options

**A — implement the consuming route.** Add `GET /scans/public/<token>`,
validate the token and its `expires_at`, serve the report read-only without a
session, and populate the link panel on success.

**B — remove the Public Link tab** until A is done, leaving internal sharing
intact.

**Recommendation: B for 2.0.** Option A means adding a deliberately
unauthenticated route that serves scan reports — including findings about a
prospect's infrastructure — days before a coordinated release tag. That
deserves its own design and security review (token entropy, expiry enforcement,
revocation, rate limiting, whether the report is redacted, `robots.txt` and
caching behaviour), not a rushed implementation inside release polish. Option B
is a small template change that removes a promise the product cannot keep.

Shipping 2.0 as-is is the one option I would argue against: a user who clicks
"Generate Public Link", sees "Public link generated successfully", and then
finds no link has been given a false success message about a sharing feature,
in a tool whose reports go to prospects.

## Summary

| | Defect 1 — viewer authorization | Defect 2 — public share links |
|---|---|---|
| Verified | Empirically (scan 15 created) | Empirically (404) + source search |
| Severity | Privilege boundary not enforced | Feature non-functional, false success message |
| Exposure | Authenticated internal users only | No security exposure; the token is inert |
| Age | Unknown; no viewer logic has ever existed | Since 2025-11-20 |
| Fix size | Small — one property, one gate, one template | Small (option B) / moderate (option A) |
| Recommendation | Fix before tagging | Remove UI for 2.0, implement in 2.1 |

## Note on how these were found

Both defects sat behind test cases that *passed vacuously*. The catalog aimed
`TC-AUTHZ-SMOKE-002` at `POST /` (the real endpoint is `POST /scan/new`, and
`POST /` returns 405) and asserted "no scan row created" — a condition any
wrong endpoint satisfies. The viewer gap only appeared once a fully valid form
was submitted through the browser.

Negative authorization cases need a positive control: the same request, as a
role that *should* succeed, proving the request shape is valid and the denial
came from the permission check rather than from a 405, a CSRF redirect, or
form validation. `TC-AUTHZ-FULL-004` has the same weakness and is not yet
fixed — it asserts non-admins are denied on a set of admin routes, with no
assertion distinguishing 403 from 404.

---

## Resolution — 2026-11-18

Both defects are fixed. Commit and verification detail below; the catalog case
`TC-AUTHZ-SMOKE-002` is now the regression guard for defect 1.

### Defect 1

`User.can_run_scans` and `User.can_manage_logos` (`app/models.py`) supply the
missing floor beneath `can_run_active_scans`: `admin`, `power_user` and `user`
may act; `viewer` may not. They gate `POST /scan/new` (`app/routes/main.py`),
and `POST /logos/upload`, `/logos/import/fetch` and `/logos/import/confirm`
(`app/routes/logos.py`). `import_confirm` is gated as well as `import_fetch`
because confirm is the step that actually creates the row and must not depend
on fetch having refused first. The scan form and the Add Logo button and modal
are hidden from viewers, but the server-side checks are the boundary.

Verified with a positive control, as the catalog now requires:

| | t_user (control) | t_viewer |
|---|---|---|
| `POST /scan/new`, identical 23-field payload | scan 18 created | refused, no row |
| `POST /logos/upload`, identical multipart | logo created | refused, no row |

The first attempt at this verification used a hand-built payload; the control
failed too, which meant the viewer "denial" proved nothing. The payload was
rebuilt by serialising the real form in a browser. That is precisely the
vacuous-pass trap described below, caught by the control rather than shipped.

### Defect 2

`PUBLIC_SHARE_LINKS_ENABLED = False` in `app/routes/scans.py`;
`generate_public_link` returns an explanatory flash instead of minting a token.
A feature flag rather than deleted code, so 2.1 can restore the implementation
alongside a consuming route. The tab button, tab pane and the orphaned
`copyPublicLink()` helper are removed from `scan_detail.html`. The badge that
labels an existing public share in the Current Shares list is kept, so any
rows already in a database remain visible and revocable.

Verified: tab, pane and form absent from the detail page; a direct POST is
refused, mints no token and writes no audit entry; and the control — sharing
scan 17 with `t_user2`, confirming access, then revoking it — still works end
to end.
